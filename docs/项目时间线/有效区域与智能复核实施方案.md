# “有效区域 + 智能复核”实施方案（修订版）

## 一、结论与设计边界

本方案建设两项互相衔接、但可以独立交付的能力：

```text
地块唯一有效区域
  ├─ 约束切片调度与推理结果
  ├─ 统一面积、密度和覆盖率口径
  └─ 约束地图展示、复核和既有导出
                         ↓
单 TIFF 智能复核工作台
  ├─ 载入已发布 infer 结果，或从 0 开始
  ├─ 文本 / 视觉 Prompt 多轮试推理
  ├─ 追加或替换当前范围内的 AI 候选
  ├─ 人工增删改与质量检查
  └─ 最终一次性发布 review run
```

设计边界如下：

- `effective_geom` 是地块级唯一现状值，高于时相和 TIFF；不做历史版本表。
- 有效区域必须在推理、复核、统计、地图和既有导出中持续生效。
- 智能复核第一期只支持“单图视野”，不支持地块时相内多 TIFF 联合复核。
- 一次复核会话可以包含多轮模型尝试，但只有最终发布才创建一条 `task_type=review` 的 run。
- 原始 infer run 与观测始终保留；review run 通过 `parent_run_id` 指向所基于的 infer run。
- 首期以检测框复核为交付主线，同时接收并展示 YOLOE-Seg 的实例 mask；“智能分割”作为后续明确工期，不与检测框主流程混写。
- 复核功能在现有 Web 应用内采用强模块化、路由级懒加载，不另建前端项目。
- 不复制 T-Rex Label 的页面和视觉设计，只吸收其标注工作台、交互式提示、候选确认等通用产品模式，并采用 GIS 原生交互与现有项目设计语言。

## 二、先统一项目中的数据概念

### 2.1 实际层级

当前数据库的业务层级应明确为：

```text
行政区信息（city / county / town / region_id）
  └─ 地块 tracts（region_id + tract_id 唯一）
       └─ 地块时相 tract_phases（tract_pk + phase_id 唯一）
            └─ TIFF tiffs（tiff_id + phase_id 唯一）
                 └─ 运行 runs
                      └─ 本次运行的全量观测 tree_observations
```

- “省 / 市 / 县”是行政检索和展示维度，不是当前数据库中逐级外键实体。
- `tract_id` 当前由业务命名与行政区上下文共同识别，不应表述为“市县直接构造出的 ID”。
- `tract_pk = hash(region_id, tract_id)`，不包含 `phase_id`，因此它代表稳定地块主键，符合有效区域只绑定地块的要求。
- `tract_phase_pk = hash(tract_pk, phase_id)`，代表地块的一个时相。
- `tiff_id` 代表某个时相下的一张影像；单图视野必须同时使用 `phase_id + tiff_id` 精确定位。

### 2.2 run 与正式结果

一次 infer 会创建一个 run，并把该次检测的全量结果写入 `tree_observations`；不同 run 的观测不会互相覆盖。地图、统计和导出不应笼统地使用“数据库中最新写入的 run”，而应使用显式发布的 active run。

当前结构只有 `tract_phases.active_run_id`，但一个地块时相可以包含多张 TIFF，单个字段无法严谨表示每张 TIFF 各自发布了哪个 run。用户会删除旧数据库，因此直接按最终模型重建，不设计兼容迁移：

- 新增 `tiffs.active_run_id`，作为单 TIFF 正式结果的唯一事实源。
- 删除 `tract_phases.active_run_id` 及其全部读写逻辑。
- infer/review 发布时原子更新目标 TIFF 的 `active_run_id`。
- 单图地图、台账、统计和导出统一读取 `tiffs.active_run_id`。
- 地块时相视野由该时相内每张 TIFF 的 active run 聚合，不再按 `started_at` 猜测最新结果。
- 台账每一行仍代表一张 TIFF，只展示该 TIFF 的 active run、正式株数和正式检测时间；未发布的新 run 只能在作业历史中看到。

台账增加 `运行次数` 列：

- 统计当前 `phase_id + tiff_id` 关联的 `infer/review` run 总数，包含成功、失败、取消和运行中状态；session 内的 AI attempts 不属于 run，不计数。
- 单元格显示 `N 次`，点击打开已经按当前 TIFF 过滤的运行历史。
- Tooltip 展示“成功 / 失败 / 取消 / 运行中”分项，并标识当前 active run。
- 后端在台账列表查询中一次性聚合 `run_count` 和各状态计数，禁止前端逐行发请求。

该修正既服务智能复核，也修复现有多 TIFF 时相的结果选择歧义。

## 三、功能一：划定有效区域

### 3.1 产品入口与展示

主入口放在 `/map` 地块工作区的地块信息卡。无论从地块时相视野还是单图视野进入，编辑对象始终是完整地块的同一个 `effective_geom`。

- 地块信息卡提供“编辑有效区域”。
- 单图视野进入时保留当前 TIFF 作为视觉参考，但不会把有效区域限制在该 TIFF footprint 内。
- 编辑模式自动收起左侧全局导航栏；鼠标靠近最左侧或点击窄边缘触发区时临时展开，离开后延迟收起。
- 编辑器退出时恢复用户进入前的导航栏状态。
- `/tasks` 仅显示“有效面积”和跳转入口，不重复实现编辑器。
- 智能复核页只展示有效区域边界与无效区遮罩，不在复核流程内修改它。

台账不增加掩膜状态、更新时间等额外列：

- 原“面积”列改名为 `面积/有效面积(hm²)`。
- 显示格式为 `12.3（10.8）`，两个值均使用公顷、保留一位小数。
- 两个面积相同时显示 `12.3（—）`。
- 未设置有效区域时也显示 `12.3（—）`，并通过编辑弹窗里的状态说明当前等同于完整地块边界。
- 快捷入口放在操作列“编辑”按钮唤起的弹窗中，不再增加独立操作按钮。

### 3.2 GIS 编辑工作台

编辑模式采用沉浸式地图工作台：

- 顶部：地块名称、当前参考时相/TIFF、保存、取消、未保存状态。
- 左侧工具条：选择、绘制面、增加区域、挖洞、分割、合并、删除、撤销、重做。
- 中间：卫星底图、当前时相 TIFF、地块边界和有效区域。
- 右侧：地块面积、有效面积、几何检查结果、导入入口。
- 底部：坐标、比例尺、缩放级别、当前工具和顶点数。

首期支持 `Polygon` 和 `MultiPolygon`，允许多个种植区和内部无效洞；支持顶点增删移动、面整体移动、合并、差集挖洞、切割、自身顶点吸附和 100 步撤销/重做。

保存规则：

- `boundary_geom` 是完整地块边界，也是有效区域的最大合法范围。
- `effective_geom` 必须位于 `boundary_geom` 内；少量越界提供“一键裁剪到地块边界”。
- 不以任何单张 TIFF footprint 作为保存约束。
- 保存前检查空几何、零面积、自相交、重复顶点、洞合法性、坐标范围和 CRS。
- 自动修复只处理无语义风险的问题；合并、简化、裁剪必须由用户确认。
- 未保存离开必须确认。

面积展示不在每个鼠标移动事件中做精确地理计算：拖动过程中用节流后的前端近似值，操作结束后再精算；低性能设备可配置为仅在操作结束后更新。保存时以后端计算结果为准。

### 3.3 技术选型：成熟组件 + 薄适配层

不自行开发完整 GIS 编辑引擎。建议采用：

- `Terra Draw` + MapLibre 适配器：负责绘制、选择、顶点编辑和交互状态。
- `Turf.js`：负责前端预览级 union、difference、bbox、面积和合法性辅助检查。
- `Shapely`：负责后端最终合法性、裁剪、规范化和面积计算。
- `pyogrio/GDAL`：负责 GIS 文件导入。

现有 `MapController` 是把业务代码与 MapLibre 私有 API 隔离的接口层，也称防腐层。通用地图能力继续使用它；编辑能力新建独立的 `GeometryEditorAdapter`，只封装工具切换、草稿读取、撤销重做和事件，不把第三方库的类型扩散到业务层。

这种方案的自建范围仅限 4estDS 特有的地块规则、中文界面和数据协同，不自建底层命中测试、拖拽控制点、几何布尔运算等成熟能力。

### 3.4 导入与初始化

支持：

- GeoJSON / JSON
- `.shp` 直接选择：桌面端或本地路径模式下，后端在同目录查找同名 `.dbf/.shx/.prj/.cpg`
- Shapefile `.zip`：浏览器上传时必须包含配套文件
- GeoPackage
- KML
- FlatGeobuf

浏览器的安全模型不能依靠一个上传的 `.shp` 自动读取用户未选择的 sibling 文件，因此：

- Tauri/本地路径模式支持直接选择 `.shp` 并查找 sibling。
- 纯浏览器上传支持多文件同时选择，或上传 `.zip`。
- 缺少 `.dbf/.shx` 时给出具体缺失文件提示，不静默降级。

导入流程为：解析文件和 CRS → 多图层时选择图层 → 只保留面要素 → 转到内部标准 CRS → 预览覆盖关系和面积 → 选择替换或合并 → 验证 → 覆盖当前唯一有效区域。

初始化规则从简：

- 地块创建完成后必须存在 `boundary_geom`；现有逻辑可由 TIFF footprint union 自动生成地块边界。
- `effective_geom` 为空时，业务含义等同于 `boundary_geom`。
- 用户首次进入编辑器时以 `boundary_geom` 作为草稿。
- 不再使用单 TIFF footprint 或无边界多 TIFF union 作为额外产品分支；缺少 `boundary_geom` 属于数据异常，应先修复地块资产。

### 3.5 数据模型

坚持每地块只维护一个有效区域，不增加来源字段、版本字段和历史表。`tracts` 仅新增/保留：

- `effective_geom`：唯一有效区域；空值表示与 `boundary_geom` 相同。
- `effective_area_hm2`：后端保存时精确计算的公顷面积，用于台账、统计和报表直接读取。

复用 `tracts.updated_at` 作为并发控制依据：客户端读取时取得 `updated_at`，保存时携带；如果地块已被其他请求更新则返回 `409`，提示重新加载。无需为有效区域单独增加 version 或 updated_at 字段。

`boundary_source` 继续只描述 `boundary_geom` 是自动生成还是人工维护，不增加 `effective_geom_source`。

SQLite 继续以规范化 WKT/GeoJSON 文本保存；PostGIS 部署使用 `MultiPolygon` 和 GiST。实现时同步修正当前 PostGIS schema 与现行 SQLite 模型的整体漂移，但不为本功能设计额外历史表。

### 3.6 API

统一使用稳定的地块主键 `tract_pk`，它不包含时相：

- `GET /api/v1/tracts/{tract_pk}/effective-area`
- `PUT /api/v1/tracts/{tract_pk}/effective-area`
- `POST /api/v1/tracts/{tract_pk}/effective-area/imports/inspect`

`GET` 返回 `boundary_geom`、当前实际生效的 effective geometry、`effective_area_hm2`、地块面积和 `updated_at`。

`PUT` 请求包含 geometry 与客户端读取到的 `updated_at`；响应返回规范化 geometry、精确面积、有效率、验证提示和新的 `updated_at`。

不新增有效区域专用版本、恢复和导出 API。既有台账导出能力扩展为按需包含地块有效区域图层。

### 3.7 在推理、统计和展示中持续生效

#### 推理性能策略

不生成整张 TIFF 分辨率大小的二值掩膜。每个 TIFF 只做一次坐标转换，把地块有效区域转换到该 TIFF 像素坐标，然后采用两级判断：

1. 使用 prepared geometry、bbox 和空间索引快速判断切片窗口。
2. 完全位于有效区域内的窗口直接推理；完全在外的跳过；只有边界相交窗口才按切片大小局部栅格化掩膜。

转换结果按 `tract_pk + tracts.updated_at + tiff_id + geotransform` 缓存。这样计算量与切片数和边界复杂度相关，不与整图总像素数直接相关，不会形成全分辨率掩膜的内存瓶颈。

该策略不改变现有 `sliced on the fly`：

- 普通 infer 和未来文本/视觉 prompt 推理都继续通过 rasterio window 直接从 TIFF/COG 按需读像素。
- 有效区域判断发生在 window 调度前；完全无效的 window 不读像素、不落盘、不进模型。
- 边界 window 只在内存中生成局部 mask；不先把全图切片落盘再过滤。
- 仅在调试配置显式开启时保存少量输入/结果切片，生产默认不落盘。
- review 的视口推理和整图推理复用同一 window provider、重叠策略、batch 和坐标还原流程，差别只在空间范围和 prompt 上下文。

边缘切片仍需推理，是因为一棵位于边界内的树冠可能跨过边界，若直接丢弃相交切片会造成漏检。模型完成后，以检测框中心点是否位于有效区域作为首期统一保留规则：中心在内则保留，中心在外则丢弃。该规则简单、稳定且与框大小无关。

#### 统计性能策略

- 株数、分树种株数和密度直接使用已过滤结果与 `effective_area_hm2`，查询时不做空间相交。
- 常规冠幅面积保留已入库的单木面积，不在每次打开页面时逐棵裁剪。
- 需要精确冠层覆盖率时，在 infer/review 发布阶段异步计算一次并写入 `runs.metrics_json`：先用空间索引区分内部树冠与边界树冠，只对边界树冠做 clip；按空间格网分块 union，避免所有树冠一次性全局 union。
- 地图和报表只读缓存指标；有效区域被修改后，将相关覆盖率标记为待重算，由低优先级 postprocess 作业刷新。

#### 展示与既有数据

- 地图可用半透明遮罩压暗无效区，并提供开关。
- 新 infer/review 必须按当前有效区域执行。
- 有效区域修改后不改写历史 run 和观测；当前地图加载旧结果时按新有效区域做一次服务端中心点过滤，保证现状展示正确。
- 历史 run 的可复现性不是首期目标，因此不保存有效区域版本；运行参数只记录当时的有效面积数值和 geometry 校验摘要，供排查使用。

## 四、功能二：智能复核

### 4.1 产品定位与工程边界

智能复核本质上是“基于 GIS 的 AI 标注工作台”：使用地图底图、COG 瓦片、地理坐标和超大 TIFF window read，模型切片过程对用户透明。

首期不拆成独立前端项目，原因是：

- 与现有地图、底图、TIFF 路由、登录态、主题、API 类型和台账入口高度共享。
- 独立项目会增加构建、部署、鉴权、跨应用跳转、状态同步和重复依赖成本。
- 前端是否拆仓不会降低 GPU 推理算力消耗；算力隔离应由后端模型队列解决。
- 当前最合适的是“模块化单体”：独立 `/review` 路由、独立 feature/entity/store、独立后端 review 服务和 GPU 队列，前端使用路由级 code splitting，普通页面不下载复核编辑器依赖。

当未来出现独立团队、独立发布周期、外部客户嵌入或独立权限域时，可以把该模块抽成单独前端；本期接口和模块边界需保证可提取，但不提前支付微前端复杂度。

### 4.2 首期只做单图视野

单图是第一期唯一复核范围，必须通过 `phase_id + tiff_id` 进入。暂不支持地块时相多 TIFF 联合复核，原因是：

- 视觉 prompt 天然属于具体像素坐标系。
- 多 TIFF 可能重叠、分辨率和 CRS 不同，会引入跨图候选归并、prompt 映射和发布归属歧义。
- 单 TIFF 已覆盖视口试验、全图扩散、多轮提示、人工编辑和发布的核心价值。
- 地块时相视野仍可聚合展示每张 TIFF 各自发布的结果。

### 4.3 两种初始化模式

创建复核会话时必须选择：

1. `基于已有推理复核`：读取该 TIFF 的 `active_run_id`，一次性加载其全部观测作为工作集，最终 review run 的 `parent_run_id` 指向该 infer/review run。
2. `从 0 复核`：工作集为空，不载入旧框；仍记录目标 TIFF 和时相，`parent_run_id` 可为空，或仅在用户明确选择参考 run 时设置。

旧 infer 框在第一种模式中始终作为当前工作结果展示，但不会自动成为视觉 prompt。视觉 prompt 集合只包含用户本轮明确绘制或明确选为样本的框；文本 prompt 是另一种独立输入。

### 4.4 多轮交互与 run 语义

一次 review session 可以执行任意多轮 AI 推理、手动增删改和撤销重做。每轮模型推理只是 session 内的 attempt，不创建 run，也不把候选写入 `tree_observations`。

只有用户点击“确认发布”后才：

- 创建一条 `runs.task_type=review` 的 run。
- `parent_run_id` 指向初始化时的 active run。
- 将最终工作集全量写入新的 `tree_observations`。
- review 与父 run 的观测拥有不同 `observation_id/run_id`，但 `tract_phase_pk/phase_id/tiff_id` 保持一致。
- 在同一数据库事务内将 `tiffs.active_run_id` 切换到 review run。

原 infer run、原观测和未发布作业均不删除。

### 4.5 视口试推理与扩散到全图

每轮推理提供范围切换：

- `当前视口`：只推理当前地图视口与目标 TIFF 的交集，适合快速验证 prompt。
- `整张影像`：处理整个 TIFF 的有效区域。

当前视口不是浏览器截图。前端提交地图视口的 WGS84 bbox/polygon 和缩放信息；后端与 TIFF footprint 求交，再通过 TIFF CRS 和 geotransform 转换为精确像素 window，随后按模型输入大小分块读取原始 TIFF。

- 当视口已经覆盖整张 TIFF 时，后端规范化为整图范围，避免重复切片。
- 视口试推理成功后显示“扩散到全图”，沿用同一模型、文本 prompt、视觉 prompt 规则和阈值执行全 TIFF。

视觉 prompt 扩散采用标准的“参考样本编码 → 目标窗口检索”方式：

1. 用户在原 TIFF 上框选一棵代表性树并指定树种。
2. 后端从原始 TIFF 精确读取包含该框及适量上下文的 reference chip；框坐标只属于这张参考图。
3. YOLOE 的 SAVPE/视觉提示路径把“参考图 + 正样本框 + 临时 class ID”编码为类别视觉表征。
4. adapter 缓存该表征，并用它对视口或全图的所有 on-the-fly windows 搜索相似目标。
5. 绝不把参考框的几何坐标复制或投影到后续数千个切片。

业内允许用一个视觉 exemplar 检索很多目标图像/切片，这正是 one-shot visual prompting 的用途；问题不在“一对多”，而在是否把 exemplar 正确编码为可复用语义。遥感树种受冠形、光照、季节和 GSD 影响明显，最佳实践是每个树种允许 1～5 个有代表性的 exemplar，经视口小范围验证后再扩散全图；多个 exemplar 聚合为同一业务类别，并保留各自贡献供用户剔除坏样本。

### 4.6 追加与替换

每轮 AI 结果出来后，用户必须选择合并方式：

- `追加`：将本轮去重后的新候选合并到当前工作集，不移除已有结果。
- `替换当前范围的 AI 候选`：仅替换本轮推理范围内、尚未人工确认的 AI 候选；不删除父 infer 框、人工新建框和已人工确认框。

如用户希望大范围删除旧 infer 结果，应使用筛选后的批量删除并明确确认，不能由“替换”按钮隐式完成。默认选项为“追加”。

每轮在交给用户确认前必须完成：

- 有效区域过滤。
- TIFF 边界和合法框过滤。
- 模型结果内部 NMS/WBF。
- 与当前工作集进行空间去重。
- 同一原框的类别/位置冲突识别。

### 4.7 变化统计

每轮 attempt 完成后显示精炼统计：

- 历史基线：初始化 infer run 的总株数，不分树种。
- 上轮累计变化：截至上一轮 review 的新增、删除、改类数量。
- 本轮变化：相对上一轮工作集的新增、删除、改类和冲突数量。
- 当前预计结果：确认当前轮后总株数。

最终发布确认框显示：

- 总体：基线株数、新增、删除、改类、最终株数。
- 分树种：原数量、转入、转出、新增、删除、最终数量。
- 未处理冲突、有效区域外框、无类别框等质量门禁。

### 4.8 独立导航入口与工作台布局

智能复核是一级业务模块，必须在 `NavRail` 配置独立入口 `/review`，图标和名称为“智能复核”，与地图、台账、任务并列。进入入口后先展示复核首页：最近草稿、可复核 TIFF、当前 active run、运行次数和继续/新建操作。

其他页面提供上下文快捷入口，但不是唯一入口：

- 单图地图视野中的“智能复核”。
- 作业历史中已成功 infer/review run 的“基于此结果复核”。
- 台账操作列 review 图标，仅在行已绑定有效 TIFF 时可用。

编辑场景自动收起全局导航栏，保留左侧窄触发区。工作台布局为：

- 顶部：地块、时相、TIFF、初始化模式、父 run、保存状态、发布。
- 左侧：选择、手工框、视觉找相似、文本预标注、删除、撤销/重做；“智能分割”按实施阶段和模型能力开放。
- 中间：MapLibre 底图、COG 真影像、有效区域、父结果、当前工作结果、AI 候选和 mask。
- 右侧：类别面板、标注列表、Prompt 配置、当前实例属性、候选列表和轮次统计，以 Tab/折叠面板控制密度。
- 底部：坐标、缩放、当前推理范围、数量和快捷键。
- 显示设置提供影像透明度、亮度、对比度、饱和度和框/Mask 可见性；这些只影响客户端渲染，不修改 TIFF。

颜色不同时承载“树种”和“状态”两个维度：

- 树种使用可配置的高对比色板；颜色根据稳定 category key 分配，确保同一树种跨轮次一致。
- 状态使用线型、粗细、透明度和图标区分：父结果实线、AI 新候选虚线、建议删除叉号、冲突双描边、人工确认加确认标记。
- 自动检查颜色与当前底图的对比度；同时提供统一高亮选中态，避免仅依赖颜色传达信息。

### 4.9 类别体系与旧 infer 类别

每个 review session 维护一个轻量 `category_catalog`，保存在草稿中，不单独建表：

- 基于已有推理时，从父 active run 的 `species` 去重读取全部旧类别、数量和已有颜色；空 species 归入“未分类”。
- 从 0 开始时，用户先创建至少一个类别，或通过文本预标注输入类别后自动创建。
- 类别包含稳定 key、中文显示名、模型 prompt、颜色和启用状态。
- 允许新增、重命名、换色、排序、合并类别；删除仍被框引用的类别前必须迁移这些框或转为“未分类”。
- 右侧类别列表按树种分组显示数量，支持类别和单实例显示/隐藏、只看当前类别、定位下一实例。
- 手工新建框和视觉 prompt 前必须有“当前活动类别”；画框后默认归入该类别，也可立即改类。
- 发布时 category key 映射回 `tree_observations.species`，保持现有数据结构。

父 infer 类别只是工作集初始事实，不会自动变成文本 prompt 或视觉 prompt；用户必须明确选择哪些类别参与新一轮 AI。

### 4.10 文本 Prompt：按树种文字找目标

文本 prompt 就是用户传入希望模型查找的树种/目标类别文字，例如 `桉树`、`eucalyptus tree crown`、`mangrove`。它是首期值得保留的一等能力，尤其适合“从 0 复核”和没有好 exemplar 的场景。

交互设计：

- “文本预标注”面板允许一次输入一个或多个业务类别。
- 每行区分“界面显示名”和“模型 prompt”：例如显示名为“桉树”，模型 prompt 可为 `eucalyptus tree crown, aerial view`。
- 用户可直接只填树种字符；高级描述、同义词和阈值按类别折叠配置。
- 执行前预览本轮类别、范围和阈值；执行后结果按对应业务类别进入候选层。
- 文本 embedding 对同一 prompt 集只编码一次并缓存，随后用于全部 on-the-fly windows。
- 中文是否优于英文由目标模型实测决定；界面始终中文，默认 prompt 模板允许配置英文别名，但不强制用户懂英文。

文本预标注和视觉找相似是并列工作流，不要求同时使用：文本适合按语义找树种，视觉适合难以准确命名、但外观相对稳定的树冠；两者结果最终进入同一去重和确认流程。

### 4.11 视觉 Prompt：框选样本并指定类别

YOLOE 首期视觉 prompt 只支持官方明确的正样本框：

- 用户先选择/新建业务类别，再紧密框住一棵代表性树。
- 每个框携带临时连续 class ID，adapter 将其映射到稳定 category key。
- 同一树种允许多个正样本框；不同树种可以在一次 attempt 中各自提供样本。
- 可以把工作集中的一个旧 infer 框显式转换为 exemplar，但默认不转换。
- 不设计 YOLOE 负框、正点、负点，因为当前官方视觉提示接口是 `bboxes + cls`，点不是该目标检测流程的输入。

新增独立 `ReviewModelAdapter`，不把多模态能力硬塞进普通 `BaseDetector`：

- `capabilities()`：声明 text、visual_bbox、instance_mask、point_refine、reference_embedding 和全图扩散能力。
- `load()`：加载模型、文本编码器或远程客户端。
- `prepare_text_prompts()`：生成和缓存文本 embedding。
- `prepare_visual_prompts(reference_image, bboxes, classes)`：生成和缓存视觉表征。
- `predict_batch(windows, prompt_context)`：批量推理。
- `normalize()`：统一输出像素框、类别、置信度、可选 mask、来源 window 和模型元数据。

首个真实实现为 YOLOE-26，使用项目内实际存在的：

- `.4estDS/models/multimodal/yoloe-26x-seg.pt`：默认高精度模型。
- `.4estDS/models/multimodal/yoloe-26l-seg.pt`：显存或速度优先的可选模型。
- `.4estDS/models/multimodal/mobileclip2_b.ts`：文本 prompt 编码器。

用户所述 `.4estDS/models/multimodal/yoloe-26-seg.pt` 是泛化名称，当前磁盘上没有该文件，配置和测试必须使用具体的 `x/l` 文件名。另提供 `mock_review` 做无 GPU 的流程测试。

adapter 不直接依赖 Ultralytics 内部对 `mobileclip2_b.ts` 当前工作目录的隐式查找；它使用配置中的绝对路径显式加载 `MobileCLIPTS`，生成 embedding 后通过 `set_classes(classes, embeddings)` 注入 YOLOE。实施前的只读探针已确认 26X 权重可识别为 `YOLOE/segment`，本地 MobileCLIP2 可输出 512 维文本 embedding。

### 4.12 智能分割的明确后续工期

YOLOE-26-Seg 会随检测返回实例 mask，首期需要完成 mask 预览、隐藏/显示，并验证其转换到 TIFF 像素和地理坐标后的正确性；但检测框仍是首期人工编辑与发布的主对象。

后续阶段开放左侧“智能分割”工具：

1. 用户选择一个检测框或重新框住单棵树。
2. 支持 mask 的 adapter 返回该实例轮廓。
3. 用户使用画笔增减区域、撤销重做并确认。
4. 后端简化并验证 polygon，写入 `crown_geom/geom_crown`，同时由 mask 外接矩形同步更新检测框。

正点/负点只在未来接入支持 point refinement 的分割模型（例如 SAM 类 adapter）时出现：正点表示“这里属于目标”，负点表示“这里是背景”，用于修正单个实例 mask；它们不是 YOLOE 目标检测的类别 prompt，也不进入首期工具栏。

### 4.13 人工编辑与快捷操作

支持框的选择、移动、缩放、新建、删除、改类、备注；支持单条和批量接受/拒绝、按范围/类别/状态筛选、撤销/重做和离开保护。

建议快捷键：`A/D` 前后候选、`Enter` 接受、`Backspace` 删除、数字键切类别、`Ctrl/Cmd+Z` 撤销、`Shift+Ctrl/Cmd+Z` 重做。输入框获得焦点时禁用冲突快捷键。

## 五、从简的数据与状态设计

### 5.1 只新增一张会话表

不新增 `review_candidates`、`review_operations`、`review_session_items` 三张关系表。只新增 `review_sessions`：

- `session_id`
- `phase_id`
- `tiff_id`
- `base_run_id`
- `mode`：`based_on_active` / `from_scratch`
- `status`：`editing` / `analyzing` / `ready` / `published` / `canceled`
- `draft_path`
- `revision`
- `created_at` / `updated_at`
- `published_run_id`

数据库只保存会话索引和生命周期，不逐框写草稿。

### 5.2 草稿与内存

开始会话时，后端一次性读取父 run 观测并构建内存工作集；从 0 模式则创建空集。多轮 AI 结果、prompt、人工增删改、候选状态和撤销命令都在会话工作集内完成。

草稿快照同时保存 `category_catalog`、类别显示/隐藏状态、当前活动类别、文本 prompt、视觉 exemplars 及其稳定 category key 映射；恢复会话后不得出现框存在但类别目录丢失的情况。

为兼顾性能和崩溃恢复：

- 活跃工作集常驻 review 服务进程内存。
- 操作以紧凑增量日志写入 `draft_path`，1 秒防抖或累计 50 次操作后原子 checkpoint。
- 周期性生成压缩快照并截断已合并日志。
- 浏览器端 Zustand 保存当前交互状态，IndexedDB 保存最近草稿镜像，用于断线提示；服务端草稿是恢复事实源。
- 所有编辑请求携带 `session_id + revision + operation_id`，实现乐观并发和幂等重试。
- 服务重启时从快照和增量日志恢复，不重新读取并重复拼接每轮候选。

最终发布才批量写数据库：创建 review run、批量插入最终全量 observations、更新 TIFF active run、完成 session 状态，全部置于一个事务中。发布失败则回滚，草稿仍可继续编辑。

## 六、API 设计

### 6.1 会话与草稿

- `POST /api/v1/reviews`：创建单 TIFF 会话，指定初始化模式和可选 base run。
- `GET /api/v1/reviews/{session_id}`：读取会话元数据、统计和恢复信息。
- `GET /api/v1/reviews/{session_id}/workspace`：获取当前视口工作集；支持 bbox。
- `POST /api/v1/reviews/{session_id}/operations`：批量提交人工/候选确认操作。
- `POST /api/v1/reviews/{session_id}/undo`
- `POST /api/v1/reviews/{session_id}/redo`
- `POST /api/v1/reviews/{session_id}/publish`
- `POST /api/v1/reviews/{session_id}/cancel`

### 6.2 AI attempts

- `POST /api/v1/reviews/{session_id}/attempts`：提交文本/视觉 prompt、viewport/full 范围和模型参数。
- `GET /api/v1/reviews/{session_id}/attempts/{attempt_id}`：进度、统计、日志和候选摘要。
- `POST /api/v1/reviews/{session_id}/attempts/{attempt_id}/cancel`
- `POST /api/v1/reviews/{session_id}/attempts/{attempt_id}/apply`：以 append/replace_ai_in_scope 合并。
- `POST /api/v1/reviews/{session_id}/attempts/{attempt_id}/expand`：沿用参数扩散到全图。

attempt 是会话内部临时任务 ID，不是 run_id；其明细保存在草稿工作区，发布后只把必要的模型和 prompt 摘要写入 review run 的 `params_json/metrics_json`。

### 6.3 地图数据

单 TIFF 首期优先使用 bbox GeoJSON 接口，不提前建设 MVT：

- 当前视口仅返回工作集和候选的简化属性。
- 编辑单个框时返回完整属性。
- 达到配置的数量阈值后启用服务端 bbox 分页和聚合显示。
- 只有真实数据规模证明 GeoJSON/bbox 不够时，再增加 MVT；避免为尚未出现的规模提前增加双写和要素 ID 映射复杂度。

### 6.4 导出

不在复核模块新增独立导出页面或格式体系。台账既有导出入口读取 TIFF active run，因此 review 发布后自动导出复核成果；只扩展既有导出服务，使其可包含有效区域并携带 `run_id/task_type/parent_run_id` 等溯源字段。

## 七、前后端模块设计

### 7.1 前端

按现有 FSD 结构增加：

- `entities/effective-area`
- `features/effective-area-editor`
- `entities/review`
- `features/review-workbench`
- `pages/ReviewPage`

关键约束：

- `/review` 使用动态 import，Terra Draw、Turf 和复核工作台不进入普通地图首包。
- MapLibre 继续负责地图、瓦片和地理坐标；不引入 Konva/Fabric 作为第二套画布坐标系统。
- Zustand 只保存高频交互状态；React Query 保存服务端会话、attempt 和 bbox 数据。
- 大数组更新使用按 ID 索引和增量 patch，不在每次拖动时复制全部观测。
- 拖动期间只更新当前图形，结束后才提交操作和执行精确检查。
- 面板、图层和快捷键均使用状态机，防止绘制/平移/选择模式冲突。

### 7.2 后端

按职责拆分：

- `EffectiveAreaService`：验证、面积、导入、保存和掩膜准备。
- `ReviewSessionService`：会话、草稿、revision 和恢复。
- `ReviewInferenceService`：视口换算、window 调度、模型调用和进度。
- `ReviewMergeService`：过滤、去重、追加/替换和统计。
- `ReviewPublishService`：质量门禁和事务发布。
- `ReviewModelAdapter`：模型可拔插边界。

复用现有 Dramatiq/Redis，新增 `review_gpu` 队列；普通 infer 和交互式 review 分队列，调度器可优先处理短视口任务，避免整图任务阻塞交互体验。模型按 adapter、weights、device 常驻缓存。

OOM 策略为降低 batch size 后重试当前批次一次；仍失败则保留已完成分块并明确报告，不无限重试。取消操作在分块边界生效，草稿不丢失。

## 八、配置项与默认值

所有可调参数集中进入 `configs/default.yaml`，环境变量仍遵循项目现有覆盖规则；前端仅从后端 capabilities/config API 读取用户可见项，不复制默认值。

建议配置：

```yaml
effective_area:
  area_refresh_ms: 120       # 编辑拖动时面积预览节流
  simplify_tolerance_px: 0.5 # 仅用于显示/建议，不静默保存
  boundary_epsilon_m: 0.05   # 浮点边界容差
  mask_cache_size: 32        # TIFF 像素几何缓存项数

review:
  default_model: yoloe
  default_scope: viewport
  default_merge_mode: append
  checkpoint_debounce_ms: 1000
  checkpoint_max_operations: 50
  viewport_max_windows: 256
  max_candidates_per_attempt: 50000
  bbox_page_size: 5000
  full_image_confirm_threshold_windows: 500
  gpu_queue: review_gpu
  session_idle_ttl_hours: 24
  models:
    yoloe:
      weights: .4estDS/models/multimodal/yoloe-26x-seg.pt
      fallback_weights: .4estDS/models/multimodal/yoloe-26l-seg.pt
      text_encoder: .4estDS/models/multimodal/mobileclip2_b.ts
      conf: 0.25
      max_visual_exemplars_per_class: 5
```

必须写清每个配置的单位、边界、性能影响和是否需要重启。模型权重、设备、batch、prompt 能力和阈值进入各 adapter 子配置，不散落在页面组件和服务代码中。

### 阶段 A：修正结果事实源

## 十、测试与验收

### 10.1 数据语义

- 验证 `tract_pk` 跨时相稳定，`tract_phase_pk` 按时相区分。
- 同一时相多 TIFF 分别发布 active run，地图/台账/统计不串图。
- `tract_phases` 不再存在 `active_run_id`；所有正式结果查询必须从 TIFF 出发。
- 台账运行次数与按 TIFF 过滤后的 infer/review 作业历史一致，attempt 不计入。
- review run 与父 run 的 TIFF/时相一致，父观测保持不变。
- 未发布 run 不影响正式地图、统计和导出。

### 10.2 有效区域

- Polygon/MultiPolygon、洞、多岛、自相交、空几何、越出地块边界。
- GeoJSON、GPKG、KML、FGB、zip Shapefile、纯浏览器多文件 Shapefile、本地 sibling Shapefile。
- 不同 CRS、缺失 `.prj`、缺失 `.dbf/.shx`、多图层和非面要素。
- 单图和地块时相入口编辑的是同一地块对象，且不受单 TIFF footprint 限制。
- 内部/外部/边界切片调度正确，中心点过滤无重复与漏写。
- 修改有效区域后密度立即按新面积计算，精确覆盖率异步重算。

### 10.3 智能复核

- 基于 active run 与从 0 两种初始化。
- 旧 infer 框可见但不自动进入视觉 prompt。
- 父 run 类别、数量和颜色正确初始化；手工框必须绑定活动类别，改类/合并/未分类流程正确。
- 文本 prompt 的显示名、模型 prompt、类别映射和 embedding 缓存正确。
- YOLOE 视觉 prompt 仅使用参考图正样本框与 class ID，多 exemplar 能稳定聚合同一树种。
- viewport 精确换算到 TIFF pixel window，覆盖整图时自动规范化。
- 多轮 prompt 的 append 和 replace_ai_in_scope 不误删父结果或人工确认框。
- 每轮过滤、NMS/WBF、与工作集去重、冲突识别和变化统计正确。
- 扩散到全图复用同一配置，不使用浏览器截图。
- 草稿断线、后端重启、重复 operation、revision 冲突和撤销重做。
- 发布原子性：run、全量 observations、TIFF active run、session 状态要么全成功，要么全回滚。
- GPU OOM 降 batch、取消和失败分块提示。

### 10.4 性能目标

- 浏览器不读取完整 TIFF，普通页面不加载复核编辑依赖。
- 有效区域不生成全分辨率掩膜。
- 视口试推理在 GPU 预热后优先返回首批候选，进度可见且可取消。
- 万级框使用增量状态和 bbox 加载保持可编辑；具体帧率和延迟阈值以目标硬件实测基线固化。
- 整图任务不阻塞视口交互任务；GPU 并发不超过配置。

## 十一、明确不做

- 不做有效区域版本表、来源字段、恢复历史和专用导出页面。
- 不做地块时相多 TIFF 联合复核。
- 不做独立前端项目或微前端。
- 不同时交付多个重型多模态模型。
- 不为候选、操作和物化结果分别建关系表。
- 不在复核模块重复建设 GIS 导出体系。
- 不在首期检测框主流程中建设多人审核分派、复杂 RBAC、模型训练、COCO/YOLO 数据集导出和 Mask 精标；智能分割按阶段 E 独立交付。
- 不提前实施 MVT；只有实测证明 bbox GeoJSON 不足时再引入。
