### 我确实把路线想歪了

您的怀疑完全正确。我在落实第二次实施方案时犯了一个**根本性的架构错误**：

> 实施方案中提出了两个 Viewer 选型方案——A（复用 map-core / MapLibre）与 B（自建轻量 Canvas Viewer）——并推荐了方案 B。**我在撰写方案时就已经把方向想偏了**，您当时回复"按你推荐的来"是基于对我专业判断的信任，但这个判断本身就是错误的。

**错误的核心逻辑链**：

1. 我错误地认为"复核工作台是单 TIFF 全屏编辑器，不需要地图底图切换"——但这忽略了一个致命事实：**项目处理的是动辄几万×几万像素的 GeoTIFF 正射影像**。一张降采样 JPEG 预览图无论如何不可能在局部放大时提供清晰的细节。这是遥感影像标注的基本常识，我不应该犯这个错。

2. 项目已有**完整的 GeoTIFF XYZ 瓦片服务基础设施**（[tiles.py](file:///home/ray/rays/repos/4estDS/src/forestds/api/routers/tiles.py)：基于 rasterio 的实时切片 + 磁盘缓存 + 并发控制），有效区域编辑器已经在正确使用它（[EffectiveAreaEditor.tsx](file:///home/ray/rays/repos/4estDS/web/src/features/effective-area-editor/EffectiveAreaEditor.tsx)：通过 MapLibre 的 `type: "raster"` source 加载 256px 瓦片）。**基础设施完全就绪，我却视而不见，另起炉灶搞了个 `<img>` 标签**。

3. 我从未真正领会"**GIS 界的类 TrexLabel 的 AI 辅助标注工作台**"的含义。TrexLabel 处理的是普通图片标注，用 Canvas/SVG 平移缩放当然可以；但本项目是**遥感 GIS 场景**——标注框有地理坐标（`box_geo`）、影像有 CRS/GSD，**图像查看器必须是地图级别的瓦片渲染器**，标注叠加层必须在地理坐标系中工作。这两者的交融才是"GIS 界的类 TrexLabel"的真实含义。

### 不只是"一些小 bug"

当前 CanvasViewer 的问题**不是小 bug 改改就行**，而是**架构级的方向性错误**：

| 维度 | 当前实现（方案 B） | 应有实现（方案 A） |
|------|---|---|
| 图像渲染 | 单张降采样 JPEG `<img>` | MapLibre + 后端 XYZ 瓦片（已有 `tiles.py`） |
| 放大清晰度 | 放大后模糊（受限于预览图分辨率） | 按需加载更高层级瓦片，无限清晰 |
| 坐标系 | 纯像素坐标 `box_px` | 地理坐标 `box_geo` + 像素坐标双系统 |
| 平移缩放 | CSS transform（有 passive event 报错） | MapLibre 原生手势（流畅无报错） |
| 与项目一致性 | 孤岛实现 | 复用 `shared/map-core` 防腐层 |

## 二、当前具体问题逐一解答

### ReviewHome 页面 (`/review`)

#### 2.1 "影像资产"列显示 `792f6 — · — (20260710)`

**核心问题**：同一 TIFF 在 Ledger 页面清楚呈现了 `市县 · 地块 · 影像名`，但在 Review 页面直接回退成横线和哈希值。

**原因**：Ledger 页面的 `list_ledger` 对 `tiffs` 与 `tract_phases` 做了正确的 `JOIN` 查询取出 `city`, `tract_id`, `file_name`；而 `reviews.py` 的 `_session_out()` 的 `JOIN` 条件不严密且未做空值回退，导致 `image_name` 和 `city` 返回 `None`。

**解决方案**：直接对标 `ledgers.py` 的 SQL 查询逻辑，完全同步 `reviews.py` 的 `_session_out()`——使用与 Ledger 一致的 `JOIN` 和 `COALESCE` 关联，保证 Review 页面草稿表格精准呈现 **`市县 · 地块 · 影像名`**。

#### 2.2 同一 TIFF 重复创建会话

**当前状态**：`session_service.py` 的 `create()` 方法完全没有排重逻辑。

**解决方案**：在 `create()` 中增加排他校验——若同一 `(phase_id, tiff_id)` 已存在 `status='active'` 的 Session，则：
- 同模式 → 直接返回现有会话（幂等）
- 不同模式 → 提示用户"该 TIFF 已有进行中的 XX 模式复核，请先完成或删除后再创建新模式会话"

## 四、核心工具行为与 AI 推理交互重设计

### 4.1 手绘画框（简单逻辑 ✅）

业务逻辑确实简单：
1. 用户选择 `draw` 工具 → 在地图上拖拽画矩形
2. MapLibre `mousedown/mousemove/mouseup` 获取起止点的 `lngLat`
3. 构造 `box_geo = [west, south, east, north]`（地理坐标）
4. 后端通过 `~geotransform` 逆仿射计算 `box_px`（全图像素坐标）
5. 创建新 ReviewItem（`source: "manual"`, `species: activeCategory`, `status: "pending"`）
6. 通过 `apply_operations` 的 `add` 操作写入工作集

唯一注意点：框坐标约束在 TIFF 有效范围内（边界裁剪）。

### 4.2 AI 辅助检测（复杂逻辑，需大幅重设计 ⚠️）

#### 当前实现 vs TrexLabel vs 新方案

| 维度 | TrexLabel | 当前代码 | 新方案 |
|------|-----------|----------|--------|
| Prompt 类型 | 仅视觉（画框即触发） | 文本 + 视觉（分离面板配置） | 文本 + 视觉（保留，但交互简化） |
| 触发方式 | 画框后**立即自动**触发推理 | 用户手动点击"执行"按钮 | **保持手动触发**（遥感大图不适合自动触发，耗时长） |
| 识别范围 | 固定全图 | 二元选择：`viewport` / `full` | **连续滑杆**：1280×1280px ~ 全图（见 §4.3） |
| 确认行为 | 确认后落实到标注列表 | "应用"按钮将候选合并到工作集 | 保留，优化 UI（见 §4.5） |
| 多轮行为 | 每轮**完全替换**全部标注 | `append` / `replace_ai_in_scope` | **新增二元选项**：`替换 / 追加(默认)`（见 §4.5） |
| 每轮是否独立 | 是（仅受当次手绘框影响） | 是（每次 attempt 独立推理） | 是 |

#### 自动触发与风险控制

- **切片基准尺寸**：来自settings相应配置项
- **【自动触发推理】开关**：
  - 在 AI 工具面板中提供一个 **`自动触发` 开关 (默认 ON)**。要有tooltip做简单解释
  - 当滑杆处于默认最左端（1280px 范围）时，自动触发体验流畅；用户画框或选择视觉样例后系统立即在后台启动推理。
  - **范围过大提示**：当用户将范围滑杆调大（如超过 2048px / 数百米）时，将有醒目的提示(非常驻)：**"⚠️ 当前识别范围较大（X.X m），推理耗时将显著增加"**，确保用户充分知悉。
  - 用户可随时关闭自动触发，改为手动点击按钮执行推理。当自动触发按钮on时, 手动按钮是隐藏的

### 4.3 识别范围滑杆与高级 UI 交互

> 注意: 新前端代码实现时, 其UI风格要完美适配现有的风格, 比如亮暗主题适配, 苹果风, 毛玻璃....

#### 交互设计

取消原来的 `viewport / full` 二元 Radio，替换为**连续范围滑杆**：

```
┌─────────────────────────────────────────────────────────────┐
│  AI 辅助设置  [自动触发 🔘]                                    │
│                                                             │
│  模式切换  [ 追加模式 | 替换模式 ]  (iOS 毛玻璃风格胶囊按钮)       │
│                                                             │
│  识别范围  ──────────○───────────   [  51.2 ] 米              │
│            (51.2 m)              (全图)                     │
└─────────────────────────────────────────────────────────────┘
```

#### UI 细节要求

- **模式切换按钮**：`追加 / 替换` 做成 iOS 风格毛玻璃胶囊切换按钮（`backdrop-filter: blur` + 半透明背景），按钮的titile是`写入模式`, info circle是`推理得到的检测框加入工作集的方式: 只追加新识别到的; 或全量替换旧工作集`, `追加 替换`4个字写在按钮内。
- **滑杆数值呈现**：尽管内部以像素为单位（左端 1280px），前端一律换算为用户易懂的**米制长度（保留 1 位小数）**，换算公式：`米 = 像素 × GSD`。
- **手动输入框**：滑杆右侧附带一个表示`输入`的小图标, 点击后展开一个紧凑输入框，支持用户直接键入米制边长值，输入后滑杆位置同步更新。
- **位置**：仅当 AI 工具（文本/视觉）激活时，浮现在画布区域右上角或底部工具条上方
- **滑杆左端（默认）**：以"识别起点"为中心的 1280×1280 像素正方形 
- **滑杆右端**：全图 `(0, 0, tiff_width, tiff_height)`
- **中间值**：对数映射，`side = 1280 × (max_side / 1280) ^ (slider_position / 100)`，确保小范围时分辨率足够
- **识别起点**：当前地图视口中心点 → 通过 `map.getCenter()` 获取 `lngLat` → 后端 `viewport_to_pixel_window` 转为像素坐标 `(cx_px, cy_px)`
- **范围矩形**：以 `(cx_px, cy_px)` 为中心，向四方各扩展 `side/2`，然后 `clamp` 到 `[0, tiff_width)` 和 `[0, tiff_height)` 的有效范围

#### 辅助可视化

- 在 MapLibre 上叠加一个**虚线矩形图层**（`line-dasharray`）,颜色要浅，实时跟随滑杆值更新
- 矩形右下角用 `maplibregl.Marker` 或 HTML Overlay 显示简洁的尺寸标注：`3840×3840 px [换行] 38.4×38.4 m`（米制宽高 = 像素宽高 × GSD）
- 增加一个按钮, 用于在`文本/视觉prompt`下让用户决定显示/隐藏该图层, 默认隐藏
- 非隐藏时, 移动/缩放地图时，矩形中心跟随视口中心实时更新


#### 前后端接口变更

当前 `scope` 字段：`{ type: "viewport" | "full", bounds?: [w,s,e,n] }`

改为：`{ type: "region", center_px: [cx, cy], side_px: number }` 或 `{ type: "full" }`

后端 `_scope_window` 方法相应适配：
```python
if scope_type == "region":
    cx, cy = scope["center_px"]
    half = scope["side_px"] / 2
    x1 = max(0, int(cx - half))
    y1 = max(0, int(cy - half))
    x2 = min(width, int(cx + half))
    y2 = min(height, int(cy + half))
    return x1, y1, x2 - x1, y2 - y1
```

### 4.4 推理过程中的有效区域过滤

#### 当前推理管线 (`engine/infer.py`) 已具备的能力

项目的 Infer 页面的推理管线（`EffectiveWindowFilter`）已经实现了三级过滤：
1. **窗口级**：`outside` → 跳过整个 Tile；`boundary` → 生成局部掩码清零有效区域外像素
2. **检测框级**：框中心点不在 `effective_geom` 内 → 剔除
3. **发布校验**：`publish_service._validate_effective_area` 再次校验

#### 复核推理的差距

当前 `inference_service.py` 的 `run_attempt` 方法**缺少**有效区域过滤：
- 没有加载 `EffectiveWindowFilter`
- 没有跳过 nodata/外区域的切片
- 没有日志记录切片统计

#### 方案

在 `run_attempt` 中整合 `EffectiveWindowFilter`：

1. 加载 `effective_geom`（从 `tracts` 表获取，已有 `load_effective_window_filter` 工具函数）
2. 对每个切片窗口执行 `classify`：
   - `outside` → 跳过
   - `boundary` → 生成局部掩码
   - `inside` → 正常推理
3. 对候选框执行中心点判定（`keep_detection`）

> **跨边界切片的阈值**：当前 `engine/infer.py` 的 `EffectiveWindowFilter.classify` 已经采用"窗口与有效区域的面积交集比例"进行判定——比例 > 0 即为 `boundary` 而非 `outside`。这个逻辑对跨边界切片是合理的（宁可多推理也不漏框），保持不变。

> **有效区域可视化**：在 MapLibre 地图上增加一个可切换的半透明图层，显示 `effective_geom` 边界。复用项目现有的 `EffectiveAreaEditor` 中 `effective-boundary-fill` / `effective-boundary-line` 图层样式。增加一个 ToolRail 按钮控制可见性。

> **Infer 页面的日志留痕**：`tasks/infer.py` 的 `run_infer_pipeline` 已调用 `load_effective_window_filter`，`run_inference` 内部有 `n_outside` 和 `n_boundary` 统计。确保这些统计在 Infer 页面的推理任务中通过后端 `logger` 打印即可（仅日志打印，不做持久化）。Review 页面无需日志留痕。

### 4.5 多轮对话与合并策略

#### 多轮流程

```
用户给出 Prompt → 后端推理（scope 内切片(sliced on the fly)推理 + WBF 融合）
       → 候选框浮现在地图上（虚线，半透明填充）
       → 用户确认/取消
       → 确认后按「替换/追加」合并到工作集
       → 用户可继续给出新 Prompt → 再推理 → 再确认 → ...
```

#### 二元选项：`替换 / 追加(默认)`

- **位置**：与识别范围滑杆放在一起（同一浮层面板），仅 AI 工具激活时可见
- **默认值**：追加

**替换模式**（简单）：
- 丢弃工作集中所有现有标注框
- 本轮推理结果直接成为新的工作集全量
- 等价于当前 `replace_all: true` 的 Patch

**追加模式**（需差集计算）：
1. **固化现有框**：所有已有标注框标记为 `frozen: true`，视觉上统一为**无填充色**, 是圆形的恢复成原始尺寸的矩形, 保持按种类着色的边框色
2. **求差集**：对本轮推理产出的候选框集合，排除与现有框重叠度 ≥ IoU 0.7 的框（视为重复），剩余为真正的"新增"
3. **新增框**的视觉呈现：**有填充色**(很浅的半透明), 圆形(只是改形状以增强视觉差异, 不是修改该对象的原始信息)，框线颜色按种类着色，与已冻结框形成明确视觉区分
4. 确认后，新增框追加到工作集，`frozen` 标记保留（后续轮次持续有效）

#### 差集计算开销分析

项目已有 `_SpatialIndex`（[merge_service.py](file:///home/ray/rays/repos/4estDS/src/forestds/review/merge_service.py)）：64px 网格空间索引。

典型场景：5000 个现有框 + 1000 个候选框：
- 空间索引构建：O(5000) 次 insert → ~1ms
- 每个候选框查询：平均命中 ~5 个邻居 → 5 次 IoU 计算
- 总计：1000 × 5 = 5000 次 IoU（每次 ~10 条浮点运算）
- **预估耗时：< 5ms**

> **结论：差集计算开销极小，完全可以在后端同步完成，结果秒出。** 无需异步或特殊优化。现有 `ReviewMergeService.apply()` 的 `append` 模式已经做了基于空间索引的去重，只需微调即可支持"冻结 + 差集"语义。

#### 前后端接口变更

`merge_mode` 枚举扩展：`"append"` | `"replace_all"` | ~~`"replace_ai_in_scope"`~~

- `replace_all`：完全替换（原 `replace_ai_in_scope` 语义太绕，直接用 `replace_all` 更直观）
- `append`：冻结现有 + 差集追加

ReviewItem 新增字段：
```typescript
interface ReviewItem {
  // ... 现有字段
  frozen?: boolean;    // 是否已冻结（追加模式下的历史框）
}
```

冻结框的行为约束：
- 不可删除、不可修改 `box_px`/`box_geo`/`species`
- 但可修改 `status`（接受/拒绝）和 `note`（备注）
- 视觉上：无填充色 + 边框降低透明度 + 都是矩形

### 4.6 推理结果的坐标与后处理开销

#### 从「推理产出」到「展示到图里」的流程

1. 模型输出：切片内局部像素坐标 `[x1_sub, y1_sub, x2_sub, y2_sub]`
2. 偏移到全图：`box_px = [x1_sub + win.x, y1_sub + win.y, ...]`（纯加法，O(1)）
3. WBF 融合去重：`weighted_box_fusion(candidates, 0.6)`（已有空间索引，O(n log n)）
4. **像素 → 地理坐标**：`box_geo` 通过 `geotransform` 仿射变换（2×2 矩阵乘法 × 4 角点，O(1)/框）
5. 前端渲染：MapLibre `GeoJSON source` 接收 `box_geo` 坐标数组，原生渲染

#### 开销评估

| 步骤 | 1000 个框的耗时 | 瓶颈？ |
|------|:-------:|:------:|
| 像素偏移 | < 0.1ms | 否 |
| WBF 融合 | ~10ms | 否 |
| 仿射变换 box_px→box_geo | ~1ms | 否 |
| `crown_width_geo` 等属性计算 | ~5ms | 否 |
| MapLibre GeoJSON 渲染 | ~20ms（GPU） | 10K+ 框时需注意 |

> **结论：开销不大。** 对于常规复核场景（< 10K 框），从推理完成到画面渲染的延迟 < 50ms。无需异步或分批加载。
>
> 对于超大量级（> 10K 框），MapLibre 支持 `filter` 表达式按视口范围动态过滤渲染，不会出现性能问题。

#### `tiffs` 表属性的计算时机

`crown_width_geo`、`crown_area_geo_est`、`crown_volume_geo_real` 等属性**仅在发布时计算**（`publish_service.py` 的 `_build_observation_row`）。复核过程中无需实时计算这些值，不影响交互体验。

## 六、新增功能：地图上的批量操作

### 6.1 多选方式

| 方式 | 交互 | 实现 |
|------|------|------|
| Ctrl+点击 | 已有 `onSelect(id, additive=true)` | 保持，MapLibre 通过 `queryRenderedFeatures` 在 `click` 事件中识别被点击的框 |
| 框选区域 | 选择工具下，按住鼠标拖拽画出矩形选区 → 选中区域内所有检测框 | MapLibre `queryRenderedFeatures(bbox)` 一次性返回矩形内所有 feature，提取 `id` 存入 `selectedIds` |

### 6.2 批量操作条

当 `selectedIds.length > 0` 时，在 TopBar 下方或画布顶部浮现操作条：

```
┌──────────────────────────────────────────────────────┐
│  已选 12 个对象   [修改类别 ▾]  [批量接受]  [批量拒绝]  [删除]  │
└──────────────────────────────────────────────────────┘
```

- **修改类别**：下拉菜单选择目标种类 → 对所有 `selectedIds` 执行 `set_category` 操作
- **批量接受/拒绝**：对所有 `selectedIds` 执行 `bulk_status` 操作
- **删除**：Popconfirm 确认后执行 `delete` 操作

> 后端 `session_service.py` 的 `apply_operations` 已支持 `bulk_status`、`delete` 等操作类型，无需新增后端接口。前端需要将选中 ID 列表构造为对应的 operation 数组。

### 6.3 框选的 ToolRail 集成

- 当前 `select` 工具既承担"点击选中"又承担"拖拽平移"，语义冲突
- 拆分为：
  - **选择工具** (V)：点击选中框 + Ctrl 多选 + 框选区域。地图平移改为中键/Space+左键
  - **平移工具** (H)：纯地图平移缩放，不选中任何框
- 这与 TrexLabel 的"光标工具"/"手掌工具"分离模式一致
