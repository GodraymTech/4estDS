# 数据库设计

本文档记录 4estDS 新一代数据库模型与架构设计原则。设计目标是围绕真实业务层级建模，支持多时相遥感影像处理、单木检测与跨时相追踪。

> [!NOTE]
> 详细的数据表列定义、数据类型及外键约束已收录于代码文件 [models.py](file:///home/ray/rays/repos/4estDS/src/forestds/db/models.py) 中，每一列均附有详细的行内注释。本文档重点阐述系统核心架构判断、ID 规则、索引设计及演进路线。

## 1. 核心层级与设计判断

### 1.1 业务层级结构

系统的核心业务层级定义如下：

```text
地块 (tract)
  └── 地块时相 (tract_phase)
        └── TIFF 影像 (tiff)
              └── 单木观测 (tree_observation)

跨时相单木个体 (tree_individual)
  └── 关联多条单木观测 (tree_observation)
```

其中“单木个体 (`tree_individual`)”不属于某一张 TIFF 影像，而是代表跨时相追踪后确立的真实树木物理身份。

### 1.2 关键架构判断

* **`tracts` 边界与有效区域建模**  
  `tracts.boundary_geom` 统一为包围该地块全时相 TIFF 资产集合的外接正矩形，由系统纯自动化更新生成，不存储 `boundary_source`。
  `tracts.effective_source` 标示有效区域来源（`default` 默认 / `manual` 手工圈定）。默认下 `effective_geom` 绑定并随 `boundary_geom` 联动，其面积 `effective_area_hm2` 自动取 TIFF 数量最多的时相下所有 TIFF `area_hm2` 之和；一旦用户手动圈定，`effective_source` 切换为 `manual` 并与外接矩形解绑，面积由手绘多边形的大圆大地测量法精确计算。

* **`tiffs` 坐标与三面积持久化规范**  
  `tiffs` 表统一使用公顷（`hm²`）为面积单位，三面积独立持久化以清晰解耦物理属性与业务有效属性：
  - `footprint_area_hm2`：图像地理四角包络外框总面积（物理矩形）。
  - `area_hm2`：图像原生的**物理非-nodata像素有效面积**（影像入库估算后即固定保存，不随手绘划界改变）。
  - `effective_area_hm2`：当前划界上下文下的**最终实际生效面积**（`default` 模式等于 `area_hm2`；`manual` 模式等于 `footprint ∩ tracts.effective_geom` 空间交集面积）。
  取消存储冗余列 `center_lng`、`center_lat` 与 `area_unit`，中心点经纬度统一在后端查询输出时由 `center_geom` 内存动态解析。

* **`footprint_bbox` 与检测框职责解耦**  
  `footprint_bbox` 仅用于记录 TIFF 图像在地理坐标系下的总体覆盖外接矩形范围（`[min_lng, min_lat, max_lng, max_lat]`）。所有模型推理得到的单木检测框严格保存在 `tree_observations` 表的 `box_px`、`box_geo` 等列中。

* **简化个体状态设计**  
  当前单木个体（`tree_individuals`）仅维护长期状态（`alive / missing / removed / unknown`），不引入过渡性的 `new` 状态或额外的状态历史维表。

* **面积/体积计算配置化**  
  面积与体积计算逻辑通过任务配置参数控制（如 `area_method = bbox_product | polygon_area | mask_area`）。计算算法不作为表结构列，每次 Run 的具体算法快照统一持久化于 `runs.params_json`。

## 2. ID 与标识生成规则

| 标识符 | 格式/长度 | 生成规则与要求 |
|---|---|---|
| `region_id` | 文本 (`市_县`) | 行政区划 ID，如 `湛江_徐闻`，由路径、元数据或用户指定 |
| `tract_id` | 任意字符串 | 用户指定地块名；未指定且仅有一张正射 TIFF 时默认使用 TIFF 文件名 stem |
| `tract_pk` | 安全编码文本 | 内部主键，格式为 `{region_id}_{tract_id}` |
| `phase_id` | `YYYYMMDD` | 8 位强语义日期字符串，如 `20240520` |
| `tract_phase_pk` | 安全编码文本 | 内部主键，格式为 `{tract_pk}_{phase_id}` |
| `tiff_id` | 5 位字符串 | 基于 TIFF 四角 WGS84 坐标按 3 位小数规范化后计算哈希 |
| `run_id` | 6 位字符串 | 运行任务（推理、训练、后处理等）生成唯一哈希标识 |
| `session_id` | 字符串 | 人工复核会话唯一标识 |
| `individual_id` | 8 位字符串 | 跨时相单木追踪确定的全局唯一个体哈希标识 |
| `observation_id` | 字符串 | 单次推理/检测产生的单木观测记录主键 |

## 3. 索引与查询优化规划

为保障空间查询与多时相检索性能，数据库建立以下核心索引：

| 索引名称 | 作用目标 | 典型使用场景 |
|---|---|---|
| `idx_tracts_region` | `tracts(region_id)` | 按行政区划检索所属地块 |
| `idx_tract_phases_tract` | `tract_phases(tract_pk, phase_id)` | 获取指定地块的时相列表与时间序列 |
| `idx_tiffs_tract_phase` | `tiffs(tract_phase_pk)` | 查询某地块时相下的所有 TIFF 影像 |
| `idx_runs_tract_phase` | `runs(tract_phase_pk, status)` | 筛选及查询已发布的推理 Run 结果 |
| `idx_obs_run` | `tree_observations(run_id)` | 读取特定 Run 生成的全量单木观测结果 |
| `idx_obs_tract_phase` | `tree_observations(tract_phase_pk)` | 按地块时相聚合和展示单木数据 |
| `idx_obs_individual` | `tree_observations(individual_id)` | 提取单株树木跨时相的历史观测轨迹 |

## 4. 业务配置项与存储规范

系统针对推理计算建立通用配置选项，控制测算逻辑：

| 配置项 | 默认值 | 备选值与含义 |
|---|---|---|
| `area_method` | `bbox_product` | 树冠面积算法：`bbox_product`（宽高相乘）、`polygon_area`（多边形面积）、`mask_area`（实例分割 Mask 面积） |
| `volume_method` | 默认算法 | 树冠体积算法：基于树高与冠幅估算 |

所有的配置快照在任务执行时随 `params_json` 录入 `runs` 表，保证任何推导指标均可完全复现。

## 5. SQLite 到 PostGIS 演进路线

为确保系统支持从轻量级本地运行平滑迁移至云端/集中式空间数据库，架构设计遵循以下演进路线：

1. **SQLite 阶段（当前）**
   * 空间几何数据（`boundary_geom`, `center_geom`, `crown_geom` 等）统一以 GeoJSON 或 WKT 文本格式存储。
   * JSON 结构字段（`path_versions`, `multisource_path_versions`, `params_json` 等）以 TEXT 格式存储，应用层负责序列化与解析。
   * 跨表复杂约束由 SQLAlchemy ORM 服务层保障。

2. **PostgreSQL / PostGIS 阶段（迁移目标）**
   * 几何文本字段直接无缝迁移为 PostGIS `Geometry` 类型，开启 GIST 空间索引。
   * JSON 字段升级为 `JSONB` 类型，利用 GIN 索引支持高效 JSON 内部查询。
   * 强化数据库级别复合外键约束与触发器机制。

## 6. 验收与约束规范

* **地块唯一性**：同一 `region_id` 内 `tract_id` 唯一；不同 `region_id` 允许重名。
* **时相唯一性**：同一地块内 `phase_id`（`YYYYMMDD`）唯一。
* **TIFF 标识**：`tiff_id + phase_id` 唯一标识一张影像。
* **多源路径存储**：路径保留原始传入字符串（不做 WSL/绝对路径非法转换）；`path_versions` 和 `multisource_path_versions` 均按日期版本号解耦维护。
* **边界继承与生成**：单 TIFF 时默认使用影像边界作为地块边界；多 TIFF 时默认 `boundary_geom` 为空并等待人工指定。
* **复核会话一致性**：`review_sessions` 记录草稿路径 `draft_path` 与修订号 `revision`，发布后生成独立 `published_run_id`。
