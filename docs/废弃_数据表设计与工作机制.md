# 数据表设计与工作机制

当前默认数据库是 SQLite: `~/.4estDS/db/4estds.sqlite`。表结构由 `src/forestds/db/schema.py` 创建，读写分别集中在 `db/reader.py` 和 `db/writer.py`。

## 1. 三层单木模型

```text
tree_observations
  每次 run 的观测结果，允许同一地块多次推理、多套参数、多份结果并存
      |
      | db promote / API publish
      v
tract_trees
  地块规范单木，代表某地块当前正式版本
      |
      | track
      v
tree_individuals
  跨时相独立个体，记录生命周期、生长、新生、枯死
```

这个模型解决两个问题:

- 保留所有推理 run 的可追溯证据。
- 让前端、报告和生命周期分析可以读取当前正式版本，而不是误用某次实验 run。

## 2. 表清单

### run_logs

记录所有任务运行状态。

核心字段:

- `run_id`: 主键。
- `parent_run_id`: 父任务 ID，预留给批量/子任务关联。
- `tag`: 可读标签。
- `task_type`: `infer`、`batch`、`report`、`export`、`track` 等。
- `model_arch`: 模型后端。
- `status`: `running`、`succeeded`、`failed`。
- `started_at`、`ended_at`、`duration_s`: 时间信息。
- `input_path`: 输入路径。
- `tiles_dir`: 静态切片缓存目录。
- `params_json`: 运行参数快照。
- `metrics_json`: 运行指标。
- `error`: 失败原因。
- `host`: 主机信息预留字段。

### tracts

代表一幅影像/一个地块时相。

核心字段:

- `tract_id`: 主键。
- `name`: 影像名称。
- `acquisition_time`: 时相，通常为 `YYYYMMDD`。
- `location`: 位置标识。
- `pixel_w`、`pixel_h`: 像素尺寸。
- `gsd`、`geo_area`、`area_unit`: 空间尺度与面积。
- `crs_epsg`、`crs_wkt`、`geotransform`、`bounds_bbox`、`footprint_geom`: 空间参考与范围。
- `status`: 地块状态。
- `active_run_id`: 当前发布/激活的正式 run。

约束:

```text
UNIQUE (acquisition_time, location)
```

### tract_sources

登记地块关联的多源文件。

字段:

- `source_id`
- `tract_id`
- `source_type`: `chm`、`dsm`、`dem`、`las` 等。
- `path`
- `meta_json`

### tree_observations

保存某次 run 的最终观测结果。这里的“最终”指已经过当前 run 内的 WBF 融合去重，但仍属于 run 级观测，不等同于正式版本。

核心字段:

- `obs_id`
- `tract_id`
- `run_id`
- `species`
- `confidence`
- `box_px_sub`: 子图内检测框。
- `box_px_full`: 全图像素检测框。
- `box_geo`: 地理坐标检测框。


- `crown_w_px`、`crown_h_px`
- `crown_w_geo`、`crown_h_geo`
- `height`、`height_source`

- `center_geo`
- `source_subimage_path`
- `slice_size`
- `geom_point`
- `geom_crown`

- `crown_area_px_est`、`crown_area_px_real`
- `crown_area_geo_est`、`crown_area_geo_real`
- `crown_volume_geo_est`、`crown_volume_geo_real`

### tract_trees

地块规范单木表，用于前端和跨时相追踪的正式版本。

核心字段:

- `canonical_id`
- `tract_id`
- `individual_id`
- `species`
- `confidence`
- `geom_point`
- `geom_crown`
- `height`
- `chosen_obs_id`
- `active_run_id`
- 冠幅面积/体积字段

### tree_individuals

跨时相个体表。

核心字段:

- `individual_id`
- `location_cluster`
- `first_seen`
- `last_seen`
- `status`: `alive`、`dead` 等。
- `growth_json`: 生长轨迹和成员信息。

## 3. run 生命周期

### CLI 单图推理

```text
cli.cmd_infer
  -> service.run_inference_job(publish=False)
  -> writer.start_run_log(status=running)
  -> tasks.run_infer_pipeline
  -> writer.write_observations
  -> writer.finish_run_log(status=succeeded/failed)
```

CLI 默认不自动发布。完成后可手动发布:

```bash
uv run 4estds db promote --run-id <run_id>
```

### API/Worker 异步推理

```text
POST /api/v1/jobs/infer
  -> enqueue_inference
  -> worker infer_actor
  -> service.run_inference_job(publish=True)
```

成功后自动尝试:

```text
writer.promote_run
  -> consolidate_tract_trees
  -> UPDATE tracts.active_run_id
```

发布失败不会删除已入库观测；前端会仍然看到 run 记录，但地块正式版本可能未更新。

## 4. promote_run 做了什么

`promote_run(run_id)` 的规则:

1. run 必须存在。
2. run 状态必须是 `succeeded`。
3. 根据 run 的观测或输入路径找到关联地块。
4. 读取该 run 的 `tree_observations`。
5. 将观测整理到 `tract_trees`。
6. 回填 `tracts.active_run_id=run_id`。

`consolidate_tract_trees` 目前使用空间邻近和 bbox IoU 对旧规范木做增量更新。首次发布时直接批量插入。

## 5. 前端读取规则

地块展示默认优先级:

```text
显式 run_id > tracts.active_run_id > 最新 succeeded run
```

对应代码在 `api/routers/tracts.py` 的 `_resolve_run`。

这意味着:

- 已发布地块优先展示正式版本。
- 未发布但有成功 run 的地块仍可在前端兜底展示。
- 报告和导出端点也遵循同样逻辑。

## 6. 切片缓存

静态切片成功后，`writer.update_tiles_dir` 会把目录写入 `run_logs.tiles_dir`。

后续同一输入路径再走 `physical_slice` 时，`reader.find_cached_tiles` 会尝试复用最近的成功切片缓存:

1. 优先精确匹配输入路径。
2. 再按文件名匹配。
3. 磁盘目录必须存在且包含文件，否则不信任缓存记录。

## 7. SQLite 与 PostGIS 演进

当前几何字段以 WKT/JSON 文本保存，便于本地单机运行和测试。迁移到 PostGIS 时建议保持业务语义不变:

- `tree_observations` 仍是 run 级观测。
- `tract_trees` 仍是正式版本。
- `tree_individuals` 仍是跨时相个体。
- `active_run_id` 仍是地块当前正式版本指针。

变化应集中在几何列类型、空间索引、租户隔离和 RLS。



# 重构数据库

## codex问答

### 1
我想彻底重构数据库models, 以最优雅,最符合业内最佳实践的方式实现层级管理
- 重要概念:
    - 行政区划ID: 格式`市_县`(形如`湛江_徐闻`), 通过极致的低复杂度算法自动获得
    - 地块ID: 任意字符串, 在同一行政区划内具有唯一性, 支持用户手动指定, 或默认为其下属唯一`正射影像文件名`. 
        - 设计哲学: 把地块和TIFF解耦, 应对某一片种植区过大而无法被用户制作成一张TIFF的情况. 
        - `地块表`的列中至少要有:
            - TIFF ID集合: 其尺寸为[0,n]
            - `地块多边形`: 支持用户手动指定; 默认时: 当TIFF ID集合尺寸为1, 直接用那个TIFF的四角作为多边形; 当不为1则留空(等待用户指定).
			- `状态`: 无/半/全影像覆盖
    - TIFF ID: 格式`5位长度的哈希值`(基于TIFF四角坐标的哈希值, 计算前先规范为经纬坐标系和3位小数精度)
        - 设计哲学: 为了防止用户对同一个TIFF改路径/重命名, 用哈希值作为ID更好对吗?
		- `TIFF表`的列中至少要有:
			- `文件路径版本`: 是一个字典, 键是`读取日期`(格式`YYYYMMDD`), 值是完整路径(保持原始, 不要做任何转换(类似wslpath那种)). 如果要读该TIFF的路径, 默认直接读最新日期的.
			- `多源文件路径`: 是字典, 键是`文件类型`(如: `chm`、`dsm`、`dem`、`las` 等), 值是又是个字典, 内部套用上面`文件路径版本`的逻辑.
			- `状态`: 未/已推理
    - 时相ID: 格式`8位长度的时间戳`(形如`20260707`)
		- 设计哲学: 
			- 一个地块/TIFF可以有多个时相. 在指定的`地块+时相`下, 其`TIFF集合`里每个TIFF的时相必须相同, 这才符合实际对吧
			- TIFF_ID + 时相ID 唯一标识一个TIFF图像
		- 来自
	- 单木个体ID: 格式`8位哈希长度`, 每棵树全球唯一, 便于跨时相追踪
	- run_id: 格式`6位哈希长度`
- 我上面对概念的设计是否符合最佳实践, 需不需要改进
- 然后你彻底重构最佳的数据库: 需要哪些表, 每个表设置哪些列. 不要有历史包袱, 不要担心适配现有代码(未来代码还会依照数据的变化而修改呢), 不要有任何限制, 我要的是一个符合我项目初衷的数据库.

  核心改进点：

  1. 时相ID不是 6 位，20260707 是 8 位。建议统一叫 phase_id，格式固定为 YYYYMMDD。
  2. TIFF ID用四角坐标哈希是合理的，但 5 位太短，碰撞风险偏高。建议至少 8-10 位；如果你坚持短 ID，数据库仍应加唯一约束和碰撞检测。
  3. TIFF ID最好表示“空间覆盖单元”，而不是某个文件路径。这样同一块空间在不同时间的正射影像可以共享同一个 tiff_id，再用 tiff_id + phase_id 唯一标识具体影像。
  4. 地块和 TIFF解耦是正确的。地块是业务对象，TIFF 是影像资产，二者应通过关联表连接。
  5. 不建议把 TIFF ID集合直接作为数组列放在地块表里。最佳实践是建关联表，因为要支持多时相、多 TIFF、覆盖状态、主影像、排序、来源等扩展。
