# 4estDS 系统并发安全性与资源调度优化实施方案（完整版）

## 1. 概述与背景

本项目（4estDS）运行在**单位内网单台服务器环境**，供少量员工通过浏览器协同使用。系统的核心特征为：**低 QPS / 少量并发，但包含 AI 算力独占、高频空间矢量读写、耗时 GIS 大图处理与多人并发协作**。

本实施方案综合了前期架构排查发现的所有并发隐患与资源调度瓶颈，旨在提供一份**全面、完整、符合工业界轻量化混合系统最佳实践**的工程落地指导。

## 2. 优化点全量清单与实施细节

### 优化点 1：转 COG 任务异步化与资源排他防重锁
- **问题分析**：原 `/assets/convert-cog` 接口在 FastAPI 同步 HTTP 请求中直接调用 `prepared_cog_path(path, force=True)` 进行 CPU/磁盘密集型转换。多用户连击或并发请求会导致多个进程对同一个文件强行覆盖写，造成文件损坏或 HTTP 超时。
- **优化方案**：
  1. 在 `worker/actors.py` 中新增 `convert_cog_actor(tiff_path, db_url)` 异步 Actor，将 COG 转码移入后台 Dramatiq 队列处理。
  2. 在 `/assets/convert-cog` 接口中建立防重锁：发起转码前校验该 TIFF 的状态，若处于 `converting` 转换状态，直接返回现有任务 ID，拒绝重复并发触发。
  3. 转码完成后自动更新数据库元数据，并向任务状态机发送完成信号。

### 优化点 2：SQLite 数据库并发性能增强 (WAL 模式 + Busy Timeout)
- **问题分析**：SQLite 默认使用 Rollback Journal 模式，任何写事务都会锁住整个数据库文件。在多用户并发写或读写交替时，极易抛出 `sqlite3.OperationalError: database is locked`。
- **优化方案**：
  1. 统一修改 `src/forestds/db/` 和 API 路由中的 SQLite 连接初始化函数 `_connect` 与 `init_db`：
     ```python
     conn.execute("PRAGMA journal_mode = WAL")
     conn.execute("PRAGMA busy_timeout = 5000")
     conn.execute("PRAGMA synchronous = NORMAL")
     ```
  2. WAL 模式（Write-Ahead Logging）实现“读不阻塞写，写不阻塞读”，配合 5000ms 超时等待，彻底消除内网多人读写时的锁库报错。

### 优化点 3：Worker GPU/内存模型 30 分钟空闲 TTL 自动卸载
- **问题分析**：GPU Worker 进程在加载检测器与 Prompt 适配器后，权重无限期常驻显存/内存中。在长期无推理任务时，白白占用数 GB 的显存与系统内存。
- **优化方案**：
  1. 扩展 `src/forestds/worker/actors.py` 中的全局缓存字典 `_detector_cache` 与 `_review_adapter_cache`，为每个缓存模型记录 `last_used_at` 时间戳。
  2. 引入 `_evict_idle_models(ttl_seconds=1800)` 检查函数（默认 30 分钟）：
     - 在每次 Worker 接收并执行新任务前，自动遍历检测超过 30 分钟未使用的模型。
     - 对超时模型执行 `del` 销毁，并显式调用 `torch.cuda.empty_cache()` 和 `gc.collect()` 彻底回收硬件资源。
  3. 完美兼顾工作时间内连续交互的 **0 延迟响应** 与下班/离座后的 **硬件资源自动回收**。

### 优化点 4：大文件/大图上传防阻塞与磁盘安全保护
- **问题分析**：`uploads.py` 允许最高 4GB 影像上传，文件接收完全在 HTTP 主线程同步执行 `shutil.copyfileobj`，内网多用户同时上传时易拖垮网络带宽与磁盘 I/O，且无中断恢复与防覆盖保护。
- **优化方案**：
  1. 为大文件写入增加分块流式处理与限流保护。
  2. 上传文件先写入 `.tmp` 临时文件，写入完成后进行文件大小与格式校验，校验通过后再通过 `os.replace` 原子性重命名，防止上传被打断产生残缺文件。

### 优化点 5：复核成果发布 (`publish_review`) 乐观并发控制与写事务互斥
- **问题分析**：核查人员在复核工作台编辑完后点击“发布成果”，系统将内存草稿写入 SQLite。若两名核查人员针对同一个 TIFF 或 Phase 同时发布，缺乏互斥锁与版本校验，会导致数据覆盖与更新冲突。
- **优化方案**：
  1. 引入基于 `revision` 的乐观并发锁（Optimistic Concurrency Control）。
  2. 发布时校验客户端传入的 `revision` 是否与数据库中最新版本一致，若版本落后，抛出 409 Conflict 冲突异常，提示用户先加载最新成果；写库过程使用独占写事务保护。

### 优化点 6：有效区域 (`effective_area`) 文件写入原子替换
- **问题分析**：有效区域编辑器保存时直接覆盖写入磁盘 GeoJSON / Shapefile，无写锁。多用户同时编辑同一区域时存在文件覆盖损坏风险。
- **优化方案**：
  1. 采用 **原子替换写入 (Atomic Replace Write)** 策略。
  2. 先将修改后的空间几何数据写入 `.tmp` 临时文件，校验 GeoJSON 结构与坐标语法无误后，调用 `os.replace` 原子替换原文件，确保写入异常或并发写时不会毁坏原始数据。

### 优化点 7：静态瓦片 (Tiles) 动态切片 CPU 运算防抖与请求合并
- **问题分析**：`/tiles/{z}/{x}/{y}` 端点在 HTTP GET 请求中实时切片解算 GeoTIFF。当多人在前端地图上滑动、缩放或开启多图层时，缓存未命中时会引发大量重复切片的 CPU 耗时计算。
- **优化方案**：
  1. 在切片服务层增加进程内轻量请求合并（Single-Flight Grouping）与防抖，防止同一坐标的切片被重复并发解算。
  2. 强化静态瓦片的 HTTP 强缓存头（`Cache-Control: public, max-age=86400` 与 `ETag`），最大化利用浏览器端本地缓存。

### 优化点 8：前端状态同步机制优化与条件短轮询降频
- **问题分析**：前端多处（如 `TasksCenter` / `LedgerTable`）采用了固定 1.2 秒的高频 `setInterval` 短轮询，在没有运行中任务或标签页处于后台时依然持续发送 API 请求。
- **优化方案**：
  1. 升级为智能动态轮询（Smart Polling）：当浏览器标签页不可见（`document.hidden`）时暂停轮询；当所有任务均已到达终态（`terminal`）时自动停用轮询。
  2. 为长任务保留轻量级 SSE (Server-Sent Events) 广播推拉结合扩展点。

### 优化点 9：`/review` 交互式 Prompt 范围类型与优先级调度微调
- **问题分析**：虽然 `review_region_actor` 和 `review_full_actor` 已接入 `REVIEW_GPU_QUEUE`，但局部画框框选（`region` 快速交互）与全图全量推理（`full` 长任务）混在同一个单线程队列中时，缺乏显式的优先抢占隔离。
- **优化方案**：
  1. 在 Dramatiq Actor 定义中微调优先级参数：`review_region_actor(priority=0)`（最高优先级），`review_full_actor(priority=10)`（较低优先级）。
  2. 确保用户在视图中画框做局部 Prompt 交互时，能够插队在耗时较长的全图推理之前优先被 Worker 处理。

### 优化点 10：SQLite WAL 日志定时检查点维护
- **问题分析**：开启 WAL 模式后，随着大量矢量写入与修改，`-wal` 日志文件可能无限膨胀，逐渐影响读取性能与占用磁盘空间。
- **优化方案**：
  1. 在数据库管理模块中加入定时 WAL 检查点机制（`PRAGMA wal_checkpoint(PASSIVE)`）。
  2. 在系统启动或任务空闲时主动触发检查点清理，控制 `-wal` 文件体积，保持 SQLite 最高读写性能。

## 4. 验证与测试方案

### 1. 自动化测试 (Automated Tests)
执行全量回归测试命令：
```bash
uv run pytest tests/ -v
```
新增专项测试用例：
* `tests/test_sqlite_wal.py`：验证多线程并发读写 SQLite 不抛出 `database is locked`。
* `tests/test_model_ttl.py`：模拟 30 分钟超时，验证缓存模型被正确销毁及 `torch.cuda.empty_cache()` 被调用。
* `tests/test_cog_async.py`：并发请求 `/assets/convert-cog`，验证防重锁正确拦截重复任务。
* `tests/test_atomic_write.py`：测试有效区域保存时打断写入不会破坏原始 GeoJSON 文件。

### 2. 手动验证 (Manual Verification)
1. 模拟多浏览器窗口并发访问系统，测试多人同时点击转 COG、编辑有效区域和发布复核成果。
2. 观察任务中心（Tasks Center），确认转 COG 任务由后台异步队列平滑执行。
3. 在 GPU 显存监控（`nvidia-smi`）下验证，当停止提 Prompt 30 分钟后，GPU 显存自动释放归零。
